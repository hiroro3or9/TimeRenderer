# TimeRenderer 再構築キット（ガイド版）

TimeRenderer（WPF / .NET 10 のタイムライン型作業記録アプリ）を、**ソースコードを持ち出せない別環境で1から作り直す**ための資料です。
生成AIに渡して少しずつ実装させることを前提に、**1回のセッションで読む量が少なくて済むよう**分割しています。

このキットは**ガイド版**です。「何を作るのか、なぜそう作るのか、どこで間違えやすいか」を文章で説明します。
プロパティ表・XAML の全文・UI 文言の一覧といった**仕様の参照資料は含みません**。細部はAIの判断に任せ、要点だけを外さない方針です。

## 使い方（トークンが限られた環境向け）

1. **セッション開始時**に `AGENT_RULES.md` を渡す（約60行）
2. `plan/phases.md` から**今回のフェーズの節だけ**を渡す
3. フェーズ節の「読むガイド」に挙がっているファイルだけを渡す（1〜2本）
4. AIに実装させる → ビルド → テスト → 節末の「手動確認」を実施 → コミット
5. フェーズが1セッションに収まらない場合は、節内の「ステップ」ごとにセッションを分ける
   （ステップの区切りでビルドが通る状態になるように計画してあります）

雛形は `plan/prompt-templates.md` を参照してください。

### 渡す量を減らすコツ

- ガイドは見出し（`##`）単位で独立して読めるように書いてあります。必要な節だけ切り出して渡して構いません
- 既に実装済みのクラスは「ファイル一覧と public メンバーの一覧だけ」を渡し、中身は渡さない
- 画面の色・余白・寸法は、フェーズ1で共通スタイルを作っておけば「このスタイルを使う」の一言で揃います

## ガイド版で決まらないこと

数値・文言・レイアウトの細部は書いていないので、そこはAIが決めます。結果として、元アプリと**同じ機能・同じ考え方**のアプリにはなりますが、**画面のピクセル単位の一致はしません**。

そのままだと困る部分は、次のどちらかで補ってください。

- 元アプリのスクリーンショットを渡す（画面を作るフェーズで一番効きます）
- 「ここは元アプリではこうなっている」と一文で伝える（`prompt-templates.md` の9番）

## 完成形の規模（参考）

- 本体：C# 約2.8万行、XAML 約7千行（ファイル約190）
- テスト：TUnit で 239 件以上（純粋ロジック中心）
- 外部 NuGet パッケージ：本体は **0**（MVVM は自作）、テストは `TUnit` のみ

## このキットに含まれないもの

- **アプリアイコン**（`Assets/AppIcon.ico`、16/24/32/48/64/256px のマルチサイズ）。持ち出せない場合は作り直してください
- 既存ユーザーデータの移行ツール（JSON の項目名を元アプリと同じにすれば、`%APPDATA%\TimeRenderer` をコピーしてそのまま読めます）

## 表記ルール

- 「」で囲んだ日本語は、UI にそのまま出す文字列の**例**です。ガイド版では網羅していません
- 「（理由）」として書いてある部分は、実装判断の根拠です。AIが勝手に「改善」して仕様を変えないための注記なので、削らずに渡してください
