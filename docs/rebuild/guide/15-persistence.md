# 15. 保存とデータ保全

## 守りたいこと

このアプリのデータは、他のどこにも控えがありません。消えたら、その人の数か月分の記録が消えます。したがって保存まわりだけは、多少くどくても守りを厚くします。

避けたい事故は3つです。書き込み中に落ちてファイルが途中で切れる。読み込みに失敗したまま空のデータで上書きする。ユーザーが気づかないうちに壊れていて、気づいたときには手遅れ。

## 書き込み

保存は**アトミック**に行います。いったん一時ファイルへ書き切ってから、既存ファイルを置き換えます。置き換えの際に元のファイルを `.bak` として残します。途中で落ちても、完全な旧版か完全な新版のどちらかが必ず残ります。

さらに**日次のスナップショット**を取ります。その日最初の保存のときに、日付入りのファイル名で控えを作り、7世代を超えたら古いものから消します。`.bak` は直前の1世代しか守れないので、「3日前の状態に戻したい」に応えられません。

## 読み込みと復旧

読み込みは多段で試します。本体 → `.bak` → 新しい順にスナップショット。どこかで読めたら、そこから復旧したことを画面に出します（黙って古いデータで動き出すと、数日分の記録が無いことに後で気づきます）。

全部だめだったときは「読み込みに失敗した」という状態にして、**そのセッションでは保存を一切しません**。壊れたファイルを空のデータで上書きするのが、最悪の結末だからです。画面には「予定データを読み込めませんでした」「データを保護するため、このセッションでは保存を停止しています」「データフォルダのバックアップ（.bak）を確認してください」と出し続けます。

ファイルがまだ無いとき（初回起動）は、空ではなくサンプルデータを入れます。空の画面だけを見せても、何ができるアプリなのか伝わりません。

## 保存のタイミング

予定データと ToDo は**700ms のデバウンス**です。変更のたびにタイマーを掛け直し、操作が 700ms 止まったところで1回書きます。ドラッグやインライン入力のたびに書くのを避けるためです。

書き込みに**失敗したとき**（ディスク不足・ファイルのロックなど）は、変更を「未保存」のまま持ち続け、**30秒後に再試行**します。失敗を無視して未保存フラグを落とすと、次の変更が来るまで書かれず、そのまま終了すると消えます。逆に 700ms で再試行し続けると、書けない状態の間ずっとディスクを叩きます。再試行を待っている間に新しい変更が来たら、通常どおり 700ms のデバウンスに戻します。

アプリを閉じるときは、溜まっている保存を強制的に書き切ります。

設定・勤務記録・使用アプリはそれぞれ別のファイルに、それぞれのタイミングで保存します。設定と勤務記録は即時（変更が少なく、失うと困る）、使用アプリは5分ごと（量が多く、多少失っても影響が小さい）。使用アプリの記録は60日を過ぎたものを捨てます。

## ログ

起動・終了と、未処理の例外をテキストログに残します。行は「時刻 レベル メッセージ」と、例外なら型・メッセージ・スタックトレース。ユーザーに「落ちました」と言われたときに、これが唯一の手がかりになります。例外ダイアログにはログの保存先フォルダを出します。

ログの書き込み自体は絶対に例外を投げないようにしてください（ログを書こうとして落ちるのが一番間抜けです）。
