# 01. アプリの骨格

## このアプリは何をするものか

1日の時間の使い方を「予定」と「実績」の2種類で記録し、日/週・月・スプリント・タイムライン・統計の各ビューで見せるデスクトップアプリです。タイマーで作業時間を測って実績を作り、出勤・退勤を記録し、ToDo を管理し、記録し忘れた時間を見つけて埋める、というところまでを1つのウィンドウで完結させます。

作りの方針は3つです。

- **データは常にローカル**。`%APPDATA%\TimeRenderer` の JSON だけで完結し、ネットワークへは一切出ません
- **勝手に確定しない**。離席を検知しても記録は自動で削らず、退勤を検知しても勝手には打刻しません。必ず人に聞いてから変えます
- **取り消せる**。予定と ToDo の変更はすべて1本の履歴に積み、Ctrl+Z で戻せます

## 技術スタック

.NET 10 / C# / WPF で、本体に NuGet パッケージを一切入れません。MVVM のための `ObservableObject` と `RelayCommand` は自作します（数十行で足ります）。タスクトレイのアイコンとフォルダ選択ダイアログに WinForms を使うので `UseWindowsForms` を有効にし、Win32 コールバックを関数ポインタで受けるために `AllowUnsafeBlocks` を有効にします。

テストは別プロジェクト（TUnit のみ）で、`Microsoft.NET.Test.Sdk` は入れず `OutputType=Exe` で実行します。本体には `InternalsVisibleTo` を書いて、テストから内部コンストラクタを呼べるようにします。

## フォルダの分け方

名前空間はフォルダ名と一致させます。

- **Models** … JSON に保存されるデータと、その表示用の派生プロパティ
- **Services** … ファイル入出力、OS 監視（離席・前面ウィンドウ）、外部コマンド（git）、ダイアログ表示
- **Helpers** … 画面状態に依存しない計算。ここに置いたものはすべてテストを書きます
- **ViewModels** … `MainViewModel` の partial 群と、小さな表示用 record
- **Views / Views.Dialogs / Controls / Converters** … 画面
- **Themes** … 配色とスタイル
- **Infrastructure** … `ObservableObject` だけ

## ViewModel は1つだけにする

画面が多いので ViewModel を機能ごとに分けたくなりますが、このアプリでは **`MainViewModel` 1つ**を責務ごとの partial ファイル（約40本）に分割する形にします。

理由は、どの機能も同じ `ScheduleItems` コレクションと同じ「再計算する」「保存する」という動作を共有しているからです。ViewModel を分けると、その共有部分を仲介する仕組み（メッセンジャーや共有サービス）を作ることになり、変更のたびに2か所を触ることになります。1クラスにしておけば、たとえば「ToDo を完了したら実績の集計も更新する」がメソッド呼び出し1行で済みます。

ファイル名は `MainViewModel.Todos.cs`、`MainViewModel.WorkDay.cs` のように責務を表す名前にし、先頭コメントに「このファイルが何を担当するか」を書きます。小さな表示専用クラス（`TimelineBar`、`CalendarCellViewModel` など）は普通に別クラスで作って構いません。

画面側は UserControl 単位（`DayWeekView`、`TimelineView`、`StatsView`、`TodoPanel` …）に分け、DataContext は MainWindow から継承させます。ダイアログは `IDialogService` 経由で開き、ViewModel からは Window を直接 new しません（テストで差し替えるため）。

## 起動の流れ

`App` はコンストラクタで3種類の未処理例外（Dispatcher、AppDomain、TaskScheduler）を購読し、ログを書いてから終了します。Dispatcher 例外は「予期しないエラーが発生したため、TimeRenderer を終了します」とログの保存先を出して、異常終了させます。握りつぶして動き続けさせないのは、壊れた状態のまま保存してデータを痛めるほうが怖いからです。

テーマの切り替えは、リソースディクショナリの末尾にダーク用の色定義を足す/外すだけで行います（後から追加したものが優先されるため、ライトの定義を上書きできる）。

`MainWindow` は `DataContext = new MainViewModel(new DefaultDialogService(this))` を作り、VM のプロパティ変更・通知コレクションを購読して、トレイアイコン・状態アイコン・ミニバーを更新します。

## MainViewModel の初期化順序

コンストラクタは2つ用意します。公開側は `TimeProvider.System` と「実行時モード」で動き、テスト用の internal 側は **OS 監視も実データ読み込みも時計も起動しません**。この分離があるおかげで、統合テストで「コマンドを呼んだら Undo で戻る」といった検証が画面なしでできます。

初期化の順序には意味があります。

1. 各種コマンドの生成
2. カテゴリ・プロジェクトコード・定型タイトルの既定値を入れる（設定読み込みで上書きされる）
3. `ScheduleItems` を作り、変更監視を購読する
4. 予定データ → 設定 → 勤務記録 → 使用アプリ → ToDo の順に読み込む
   - 勤務記録は予定データの後（未退勤の自動締めが実績を参照するため）
   - ToDo は設定の後（並べ替え設定を反映するため）
5. 時計を開始し、最後に「初期化済み」フラグを立てる

このフラグが立つまで保存処理は何もしません。読み込みの途中で保存が走ると、まだ空のコレクションでファイルを上書きしてしまいます。

実装を段階的に進める間は、まだ書いていない `Initialize*` / `Load*` は**空のメソッド**として置いておきます。順序が意味を持つので、呼び出しの骨格を先に完成させておくほうが後が楽です。

## 時計

500ms 間隔の `DispatcherTimer` を1本だけ持ち、そこから必要な更新を間引いて呼びます。タイマーを機能ごとに増やすと、止め忘れと発火順の問題が出ます。

- 毎回：記録中の経過時間（と、カウントダウンが0になったら自動停止）
- 10秒ごと：定期予定のリマインダー、ToDo の通知、勤務状態の更新
- 30秒ごと：タイムラインの現在時刻ライン
- 5分ごと：未記録時間の再計算、使用アプリの書き出し
- 日付が変わったとき：表示中の日付まわりを作り直す

## 変更 → 再計算 → 保存の流れ

`ScheduleItems` の追加・削除と、各アイテムのプロパティ変更を1か所で受け、そこから「レイアウトの再計算」と「保存の予約」を行います。ここで大事なのが**抑止フラグ**です。

- 読み込み中
- 1つの操作で複数のプロパティを続けて変える最中（編集ダイアログの反映など）
- 取り消し/やり直しの適用中
- ToDo をプログラムから書き換えている最中

これらの間はハンドラを素通りさせ、操作の終わりに1回だけ再計算と保存を行います。入れないと、1回の編集で再計算が5回走り、履歴にも5件積まれます。

再計算そのものも、要求をためて**描画の直前に1回**だけ実行します（Dispatcher の Render 優先度に積む）。ドラッグ中はマウスが動くたびに要求が飛ぶので、これが無いと目に見えて重くなります。ただしテストやドラッグ確定時には即座に確定させたいので、たまっている再計算を今すぐ実行するメソッドも用意します。

保存は**700ms のデバウンス**です。文字を打つたびにファイルへ書くのを避けつつ、アプリを閉じるときには必ず書き切ります。

## ビューと ViewModel のつなぎ方

バインディングで済むものはバインディングで、済まないものだけイベントで渡します。ViewModel から画面へ「して欲しいこと」を伝える口は4つだけです。

- 指定時刻までスクロールしてほしい（日/週）
- 選択中のアイテムを見える位置まで動かしてほしい（タイムライン）
- 選択中のアイテムに合わせてズームしてほしい（タイムライン）
- ToDo のクイック追加欄にフォーカスしてほしい

逆に、ドラッグ・ヒットテスト・フォーカス・スクロール位置といった**画面固有の処理はコードビハインドに書いて構いません**。無理に ViewModel へ持ち上げると、座標計算のためだけに画面の寸法を VM が知ることになります。

## データの置き場所

`%APPDATA%\TimeRenderer` に、予定データ・設定・ToDo・ToDo のアーカイブ・勤務記録・使用アプリ履歴を JSON で置きます。バックアップ（`.bak`）と日次スナップショット、クラッシュログも同じ場所です。詳しくは `15` を読んでください。
