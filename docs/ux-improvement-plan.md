# TimeRenderer UI・UX 改善計画

作成日: 2026-08-08  
対象: TimeRenderer（WPF / .NET 10）

## 1. 目的

TimeRenderer は、予定、作業記録、勤務時間、ToDo、通知、統計、ふりかえりなど、日々の作業を一つのアプリで扱える機能をすでに備えている。

今後は単純に機能を増やすより、次の点を改善することで、日常操作の速さと分かりやすさを高める。

- 主要機能を見つけやすくする
- 「出勤」と「作業記録」の違いを直感的に伝える
- 通知や設定による画面の圧迫を減らす
- ライト／ダークテーマの完成度と可読性を高める
- 大きくなった ToDo 周辺のコードを安全に変更できる構造へ整理する

## 2. 現状の強み

改善時に残すべき長所は次のとおり。

- 今日、日、週、月、スプリント、タイムライン、統計、ふりかえりの複数ビュー
- ライト／ダークテーマと共通スタイル
- 検索とカテゴリフィルター
- ToDo のクイック追加記法と入力中プレビュー
- 出勤／退勤と作業記録を別の概念として管理する設計
- 離席検知、使用アプリの記録、未記録時間の補完
- データのデバウンス保存、アトミック書き込み、バックアップ管理
- 予定のドラッグ操作、Undo／Redo、キーボード操作

大規模な機能刷新ではなく、これらを保ったまま情報設計と表示方法を整える。

## 4. 表示モードのナビゲーション再設計

### 現状

ツールバーのドロップダウンに、次の8モードが同じ階層で並んでいる。

- 今日
- 日
- 週
- 月
- スプリント
- タイムライン
- 統計
- ふりかえり

画面を広く使える一方、ドロップダウンを開くまで利用できるビューが分かりにくい。

### 提案

主要機能を次の4グループへ整理する。

1. ホーム
   - 今日
2. カレンダー
   - 日
   - 週
   - 月
3. スプリント
   - カレンダー
   - タイムライン
4. 分析
   - 統計
   - ふりかえり

通常幅ではアイコンと名称を持つ左ナビゲーション、狭い幅ではアイコンのみの表示を想定する。グループ内の表示切替は、各画面上部のセグメントボタンで行う。

### 完了条件

- 利用可能な主要画面が、ドロップダウンを開かなくても分かる
- 現在位置が色と選択表示で明確に分かる
- ウィンドウ幅が狭いときもメイン領域を過度に圧迫しない
- 現在の表示モードと日付位置が設定に保存される
- 既存の前へ／次へ／今日の動作を維持する

## 5. 記録状態を示すフォーカスバー

### 現状

出勤／退勤、作業記録、表示モード、ToDo、設定が同じツールバーに並ぶ。出勤と作業記録は別の概念だが、初見では区別しにくい。

### 提案

ツールバーの責務を次のように分ける。

- 出勤／退勤: 控えめな勤務ステータスとして表示
- 記録前: 青系の「記録開始」を主操作として表示
- 記録中: タイトル、カテゴリ、経過時間、停止を一つのフォーカスバーへまとめる
- 赤色: 記録停止など、停止・中断を意味する状態に限定する

記録中はアプリ内のどのビューへ移動しても、現在記録している内容を見失わないようにする。

### 完了条件

- 出勤状態と作業記録状態を一目で区別できる
- 記録中のタイトルと経過時間が常に確認できる
- 記録開始と停止で色の意味が矛盾しない
- キーボードとトレイからの既存操作を維持する
- 記録中タイトルの直接編集を維持する

## 6. 通知センターへの集約

### 実装状況（2026-08-08）

- `NotificationHost` を追加し、通常通知を画面右上のカード型オーバーレイへ移した
- 通知領域に最大高を設け、件数が多い場合は通知領域内でスクロールするようにした
- データ読み込み・復元の通知は、通常通知と分けた継続表示にした
- 警告色を意味ベースのテーマリソースへ移し、ライト／ダークテーマで個別に定義した
- 通知履歴、未読件数、ベルアイコンから開く通知一覧は未実装

### 現状

メイン画面上部には、次の通知が個別のバナーとして縦に積まれる。

- 定期予定のリマインダー
- ToDo リマインダー
- 見逃した ToDo 通知
- ToDo のまとめ通知
- 自動記録開始通知
- 離席通知
- データ読み込み・復元通知

複数の通知が同時に出ると、予定やタイムラインの表示領域が小さくなる。

### 提案

通知を次の2種類へ分ける。

#### 一時通知

画面右上のトーストとして表示し、同時表示は最大3件とする。

- リマインダー
- ToDo 通知
- 自動記録開始
- 離席検知

表示しきれない通知は通知センターへ格納し、ベルアイコンから確認できるようにする。

#### 継続通知

対応するまで画面上部に残す。

- データ読み込み失敗
- バックアップからの復元
- 保存不能など、データ保全に関わる異常

### 実装方針

- `NotificationItem` でタイトル、本文、重要度、操作、期限を共通化する
- `NotificationHost` を独立した UserControl として作る
- 通知の生成と表示を `NotificationService` 経由にする
- 警告色は直接指定せず、意味ベースのテーマブラシを使う

### 完了条件

- 通常通知がメイン領域の高さを継続的に奪わない
- データ保全に関わる通知は自動で消えない
- 通知ごとの記録開始、完了、先送りなどの既存操作を維持する
- ライト／ダークテーマの両方で通知が読みやすい

## 7. 設定とデータ管理の分離

### 実装状況（2026-08-08）

- `ManagementPanel` を追加し、分類・定期予定・スプリントの専用導線を設けた
- カテゴリ、プロジェクトコード、定型タイトルを「分類」タブへまとめた
- 設定パネルを320pxから400pxへ広げ、一般設定に専念する表示へ変更した
- ToDo、設定、管理の各パネルが同時に重ならないよう表示状態を連携した
- 管理パネルの開閉状態を設定ファイルへ保存するようにした
- 設定検索と、設定XAML内に残る移行前の非表示定義の削除は未実装

### 現状

幅320pxの設定パネルに、一般設定とマスターデータ管理が混在している。

設定に含まれる主な内容:

- 外観
- 表示時間と曜日
- 離席・中断の検知
- 使用アプリの記録
- ToDo 通知
- 勤務の記録
- カテゴリ
- プロジェクトコード
- 定型タイトル
- 定期予定
- スプリント

カテゴリや定期予定の編集は、環境設定というよりデータ管理に近い。

### 提案

#### 設定パネルに残すもの

- 外観
- カレンダー表示
- 離席検知
- 使用アプリの記録
- ToDo 通知
- 勤務とふりかえり
- データ保存先とバックアップ

#### 管理画面へ移すもの

- カテゴリ
- プロジェクトコード
- 定型タイトル
- 定期予定
- スプリント

設定パネルは400～440px程度へ広げ、設定名検索を追加する。管理画面は一覧と編集領域を十分に確保できる独立画面またはダイアログにする。

### 完了条件

- 歯車アイコンの中に一般設定がまとまっている
- カテゴリや定期予定の管理場所をナビゲーションから発見できる
- 長い説明文や入力欄が不自然に折り返されない
- 設定名の検索から該当セクションへ移動できる

## 8. テーマとアクセシビリティ

### 提案するテーマトークン

- `SuccessBrush`
- `SuccessSubtleBrush`
- `WarningBrush`
- `WarningSubtleBrush`
- `WarningTextBrush`
- `InfoBrush`
- `InfoSubtleBrush`
- `OverlayBrush`
- `FocusVisualBrush`
- `NowIndicatorBrush`

警告バナーや現在時刻線などの色を直接指定せず、ライト／ダークテーマで個別に定義する。

### 文字と操作領域

- 重要な補助情報は原則12px以上にする
- `TextMutedBrush` は装飾的な情報に限定する
- 操作に必要な説明は `TextSecondaryBrush` を使う
- アイコンだけのボタンには必ず ToolTip とアクセシブル名を付ける
- キーボードフォーカスを背景色だけでなく輪郭でも示す
- 頻繁に押すボタンは十分なクリック領域を確保する

### 完了条件

- ダークモードでライト用の警告色が残らない
- 小さい文字でも主要情報を無理なく読める
- Tab キーで主要操作を順番に移動できる
- キーボードフォーカス位置を常に判別できる
- Windows の高コントラスト設定でも主要操作が失われない

## 9. ToDo パネルの操作改善

### 提案

- 「今日」「期限切れ」「すべて」のフィルターチップ
- タイトルと内容を対象にしたパネル内検索
- パネル幅の変更
- オーバーレイ表示と固定表示の切り替え
- `Esc` キーでパネルを閉じる
- フィルターと並び順の保存
- 件数が多いときも選択位置を維持する

クイック追加記法、入力中プレビュー、ドラッグによる時間確保、サブタスクなど、既存の強い機能は維持する。

### 完了条件

- 期限切れや今日やる項目へ1クリックで絞り込める
- ToDo が増えても目的の項目を短時間で見つけられる
- 小さい画面ではオーバーレイ、大きい画面では固定表示を選べる
- パネルを閉じた後もフィルター状態が保持される

## 10. リファクタリング方針

### 10.1 ToDo の責務分割

`MainViewModel.Todos.cs` は、次の責務を一つの partial クラス内で扱っている。

- 一覧と選択状態
- クイック追加
- CRUD
- 並べ替え
- サブタスク
- 予定への時間確保
- 作業記録との連動
- リマインダー
- 見逃し通知
- まとめ通知
- 古い完了項目の整理
- 保存と読み込み

段階的に次の単位へ分ける。

- `TodoPanelViewModel`: パネルの表示状態、選択、絞り込み、並べ替え
- `TodoService`: 追加、編集、削除、完了
- `TodoReminderService`: 通知判定、先送り、見逃し、まとめ通知
- `TodoRecurrenceCalculator`: 次回分の計算
- `TodoSchedulingService`: 予定化、未記録時間の補完、記録との連動
- `TodoRepository`: 保存、読み込み、アーカイブ

一度に全面移行せず、通知や繰り返しなど境界が明確な処理から移す。

### 10.2 TodoItem の責務分割

現在の `TodoItem` は、保存データ、通知処理、繰り返し計算、Brush、表示文言、ToolTip 生成を持つ。

最終的には次の分離を目指す。

- `TodoItem`: 永続化する状態と最小限の不変条件
- `TodoItemViewModel`: Brush、表示文言、画面用の派生値
- `TodoRecurrenceCalculator`: 繰り返し計算
- `TodoPresentationFormatter`: 期間、進捗、ToolTip の表示文言

既存JSONとの互換性を保つため、保存モデルのプロパティ名と値の意味は変更しない。

### 10.3 ビューの分割

次の領域を UserControl または共通コントロールへ切り出す。

- `MainToolbar`
- `RecordingFocusBar`
- `NotificationHost`
- `ViewNavigation`
- `SettingsSearchBox`

ドラッグ、リサイズ、座標計算など、表示に密接な処理は無理に ViewModel へ移さない。コードビハインドの行数削減自体を目的にせず、画面単位の責務が分かれることを優先する。

### 10.4 MVVM Toolkit

CommunityToolkit.Mvvm の導入は、責務分割後に検討する。

先に全面移行すると変更範囲が大きくなる一方、直接の使い勝手は変わらない。新しい小さな ViewModel から段階的に採用し、既存の `RelayCommand` と置き換える。

## 11. 自動テスト

最初に、UIから独立して検証できるロジックへテストを追加する。

- `TodoQuickParser`
- `TodoRecurrenceCalculator`
- `ScheduleLayoutHelper`
- `TimelineScale`
- `TimelineLaneHelper`
- `SprintHelper`
- `UnrecordedGapHelper`
- バックアップ復元と壊れたJSONの読み込み
- 日付をまたぐ予定の分割
- 日付、タイムゾーン、月末、うるう年を含む境界条件

UI変更前に主要ロジックのテストを用意すると、ナビゲーションや ViewModel の分割を安全に進めやすい。

## 12. 推奨する実装フェーズ

### フェーズ1: UI polish v1

最初に行う推奨範囲。

1. 意味ベースのテーマカラーを追加する
2. ハードコードされた警告色をテーマへ移す
3. 表示モードをグループ化したナビゲーションへ変更する
4. 出勤と作業記録を分離したフォーカスバーを作る
5. 既存の通知を `NotificationHost` へ集約する

機能やデータ形式を変えず、見た目と日常操作の改善を先に得る。

### フェーズ2: パネル改善

1. ToDo のフィルターチップと検索
2. ToDo パネルの可変幅と固定表示
3. 設定パネルの拡幅と設定検索
4. 設定とデータ管理の分離

### フェーズ3: 内部構造

1. テストプロジェクトを追加する
2. ToDo リマインダー処理をサービスへ分離する
3. 繰り返し計算を純粋ロジックへ分離する
4. ToDo の保存処理を Repository へ分離する
5. 新しい ViewModel から CommunityToolkit.Mvvm を採用する

## 13. フェーズ1の検証項目

- ライト／ダークテーマの両方を確認する
- 100%、125%、150%、200% DPI で表示を確認する
- 最小幅840pxと通常幅1100px以上で確認する
- すべての表示モードへ移動できることを確認する
- 記録開始、タイトル変更、停止、Undo を確認する
- 出勤、退勤、勤務時間編集を確認する
- 各種通知の表示、先送り、完了、閉じるを確認する
- ToDo と設定のパネルが同時に重ならないことを確認する
- トレイから表示、記録、出勤、終了を確認する
- データ保存形式と保存先が変わっていないことを確認する

## 14. 対象外

初期のUI改善では次を行わない。

- 保存データ形式の破壊的変更
- 全ViewModelの一括置き換え
- 全コードビハインドの排除
- 新しいクラウド同期機能
- WebアプリやクロスプラットフォームUIへの移植
- 既存機能の大幅な削除

## 15. 成功の判断基準

改善後は、少なくとも次の状態を目指す。

- 初見でも利用できる主要画面が分かる
- 出勤と作業記録を迷わず使い分けられる
- 記録中の内容をどの画面でも確認できる
- 通知が重なって作業領域を隠さない
- 設定とデータ管理の場所が直感に合う
- ライト／ダークテーマの品質差がない
- ToDoが増えても目的の項目を見つけやすい
- UI変更を支える自動テストと責務分割が進んでいる
